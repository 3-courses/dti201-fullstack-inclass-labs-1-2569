02 · Event loop

Asynchronous ทำให้ “รอได้โดยไม่หยุดทั้งหน้า”

JavaScript เริ่มงานเครือข่าย แล้วคืนการควบคุมให้ main thread เพื่อรับ click, scroll และวาด UI ต่อ เมื่อ response พร้อม callback ของ Promise จึงกลับเข้าคิว

ชั้นการทำงานหน้าที่ความเข้าใจผิดที่พบบ่อย
Call stackรัน JavaScript ทีละงานไม่ได้แปลว่าทุกอย่างบน browser มี thread เดียวทั้งหมด
Web APIsดูแลงาน timer, network และ event ภายนอก stackfetch() ไม่ได้นั่งรออยู่ใน stack
Microtask queueเก็บงานต่อจาก Promise.then() ไม่ทำงานทันที ณ บรรทัดที่เขียน
console.log("1 เริ่ม");
fetch(url).then(() => console.log("3 response พร้อม"));
console.log("2 หน้าเว็บยังทำงานต่อ");
คำทำนายก่อนรัน ลำดับมักเป็น 1 → 2 → 3 เพราะ fetch() คืน Promise ทันที ส่วนงานใน .then() รอจน Promise resolved
03 · API literacy

อ่าน Request URL ให้เป็น ก่อนเขียน Fetch

URL ที่ดีตอบได้ 4 เรื่อง ได้แก่ server อยู่ที่ใด ใช้ endpoint ใด ส่งเงื่อนไขอะไร และยืนยันสิทธิ์อย่างไร

https://developer.nps.gov/api/v1/parks?stateCode=CA&limit=10&api_key=YOUR_KEY
└──────────── base URL ────────────┘└endpoint┘ └──── query parameters ────┘

Checklist ก่อนทดลอง

อ่าน documentation → เลือก endpoint → ตรวจ method → ระบุ required parameters → ทดลอง response → สำรวจ JSON shape

API key คือข้อมูลลับหรือไม่

Key ฝั่ง client มองเห็นได้เสมอ อย่าฝังคีย์ที่มีสิทธิ์สูงใน JavaScript จริง ควรจำกัด domain, quota และ proxy ผ่าน backend เมื่อจำเป็น

ประกอบ URL แบบปลอดภัย

เลือกค่าแล้วกด “สร้าง URL”
04 · Fetch pipeline

Fetch สำเร็จ 2 ชั้น จึงจะได้ข้อมูล

ชั้นแรกได้ Response ซึ่งบอกสถานะและถือ body stream ชั้นที่สองใช้ response.json() เพื่ออ่าน stream และแปลง JSON เป็น object

async function loadParks(url) {
  const response = await fetch(url);
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }
  const data = await response.json();
  return data;
}

05 · Resilience

fetch() ไม่ reject เมื่อเจอ 404 หรือ 500

Promise จะ reject เมื่อ request ไปไม่ถึงปลายทาง เช่น network ขาด หรือถูก block แต่ HTTP error ยังถือว่า server ตอบกลับสำเร็จในเชิงเครือข่าย จึงต้องตรวจ response.ok เอง

Network error

ไม่มี HTTP response ให้ตรวจ มักเข้า catch โดยตรง ควรแจ้งให้ลองใหม่และเก็บข้อมูล input ไว้

HTTP error

มี status เช่น 401, 404, 429, 500 อ่าน body เพื่อหาข้อความที่เหมาะสม แล้ว throw เพื่อหยุด success path

async function requestJSON(url) {
  try {
    const res = await fetch(url);
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return await res.json();
  } catch (error) {
    // อัปเดต UI ให้ผู้ใช้รู้ว่าจะทำอะไรต่อได้
    showError(error.message);
    throw error;
  }
}
ตรวจความเข้าใจ

Server ตอบ 404 การเขียน fetch(url).catch(...) อย่างเดียวเพียงพอหรือไม่

07 · Capstone

ภารกิจ National Park Spotlight

สร้าง component ที่โหลดอุทยานตามรัฐ แสดงหนึ่งรายการแบบสุ่ม และทำให้ผู้ใช้เห็นทุกสถานะของระบบ

เกณฑ์ผ่านพื้นฐาน

  1. สร้าง request URL ด้วย URL และ URLSearchParams
  2. มี loading, success, empty และ error state
  3. ตรวจ response.ok
  4. แสดงชื่อ ลิงก์ และคำอธิบายด้วย DOM API

เกณฑ์วิเคราะห์เชิงลึก

  1. อธิบายว่า key ควรอยู่ client หรือ server
  2. ป้องกัน request ซ้ำหรือ race condition
  3. เสนอวิธีทดสอบ 200, 404, 429 และ offline
  4. อธิบายเหตุผลที่ไม่ใช้ innerHTML
กับดักการออกแบบ ถ้าผู้ใช้เปลี่ยนรัฐเร็วมาก response เก่าอาจกลับมาทีหลังและทับผลล่าสุด ลองค้นเรื่อง AbortController เพื่อยกเลิก request ก่อนหน้า
